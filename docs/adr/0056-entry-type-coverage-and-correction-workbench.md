# ADR 0056：Entry 类型覆盖与快速纠错工作台

- 状态：Accepted
- 日期：2026-09-01
- 决策者：Project owner / Main Agent

## 背景

M2-P2A–D 的真实 refresh 显示 7,528 个当前 Entry 缺少类型。M2-P2E 已允许 Codex 用外部
100 条微批次补齐，但所有者仍需要一个不依赖命令行工作包的可见入口，用来观察覆盖率、抽查既有
类型并逐条修正误判。把完整 Entry 全量加载进浏览器或为此建立第二套写协议都会重新制造规模问题。

## 决策

1. “标签”页增加“类型覆盖与纠错”模式；原文档/条目标注模式保持不变。
2. 工作台显示当前可见 Entry 总数、已分类数、缺失数和十种类型分布。默认打开缺失类型队列，也可
   按某一既有类型抽查。
3. 队列每页最多 20 条，使用 `capturedAt + snapshotId + documentOrder + entryId` 的稳定游标。
   PostgreSQL 在一个只读可重复读事务中统计并选择当前页，只 hydration 页内 Entry。
4. 类型保存复用现有 Entry CAS 修订。请求保留正文、内容关键词、领域、评分、Fragment 和隐私事实，
   只替换类型；保存缺失类型后该 Entry 自动退出默认队列。
5. 类型修订前后的单 Entry 读取优先使用现有按 ID hydration，避免每次保存加载全库。
6. 隐私 Entry 默认不计数、不显示；只有工作台本次显式勾选后才进入相应统计和队列。
7. 前端为每次读取使用取消信号和请求代次，旧响应不得覆盖较新的筛选、分页或隐私范围。

## 结果与边界

- P2F 是所有者可见的类型覆盖与纠错 UI，不替代 P2E 的大批 Codex 复核。
- 没有迁移、新依赖、Provider、后台循环、自动改写或第二套分类数据结构。
- 领域缺失、平局和无信号仍可由 P2E 工作包处理；如需专门 UI，必须由后续实际使用证明必要。
- 合成测试覆盖统计、游标、隐私参数传递、PostgreSQL 页内 hydration、闭合 API 和 Web 路由；
  自动化测试不读取或改写所有者真实资料。

## 实施后只读评测

所有者授权在现有本地 Docker 私人部署上进行只读效果评测。14,910 条公开当前 Entry 中，4,195 条
已有类型，10,715 条缺失，类型覆盖率为 28.14%。工作区没有私密 Entry，因此真实私密行不被用于
验收，私密排除与显式加入继续由合成回归覆盖。

缺失队列首屏只 hydration 20 条 Entry、20 条 Fragment input、64 条内容关键词和 17 条领域行；全量
相应集合为 14,910、14,910、47,784 和 11,222 行。一次本地 PostgreSQL 18.6 代表性测量中，coverage、
page、core、inputs、keywords 和 domains 六段产品等价 SQL 分别为 5.037、8.331、7.055、7.083、
6.915 和 5.342 ms，合计约 39.8 ms。该单次本地结果只证明页内读取边界生效，不构成部署 SLA。
评测没有修改正文、标签、偏好或数据库状态，也没有输出真实正文、标识或来源。

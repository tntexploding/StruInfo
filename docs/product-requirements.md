# StruInfo 产品需求

- 状态：方向已更新；首个领域、信源和自动化边界待确认
- 最近更新：2026-08-02
- 目的：定义“AI 原生在线个人信息枢纽”的产品边界与候选 MVP
- 历史基线：[产品需求 v0.1](archive/product-requirements-v0.1.md)

## 1. 本次方向变化

v0.1 将 StruInfo 定义为可追溯的知识结构化工作台。这个内核仍然成立，但它现在只是更大产品中的“知识库核心”。

v0.2 将产品扩展为：持续采集外部信息、由 AI 主动加工、形成可核验知识、支持本地与在线查询，并向用户或其他项目主动推送结果的个人信息枢纽。

## 2. 产品定义

### 一句话定位

> StruInfo 是一个 AI 原生、来源可追溯的在线个人信息枢纽：它持续从用户指定或系统发现的信源获取信息，保存当时的来源证据，由 AI 完成筛选、总结、结构化与关联，再通过知识树、时间线、问答和日报/周报供用户查询、审核、入库与推送。

这是长期愿景。首个切入产品更窄：**面向个人的专业信息监测与沉淀工具**，先解决“持续跟踪已知信源，并把值得保留的更新变成可追溯知识”。

本文中的“在线”需要区分三层：

1. **能够访问互联网信源**：产品核心要求；
2. **通过浏览器使用**：首轮可以是只在本机或局域网访问的 Web 应用；
3. **由公网云服务器托管**：后续部署目标，是否进入第一可用版本仍待确认。

### 核心任务

> 当我需要长期跟踪某个领域时，我不想每天手工巡视网页、复制内容、整理笔记并重复寻找旧资料。我希望系统持续收集值得关注的信息，由 AI 结合我的既有知识进行分析，给出带出处的摘要和更新；高风险内容由我一键确认，低风险内容可按规则自动处理，并能把结果可靠地发送给我或我的其他项目。

### 核心价值

StruInfo 的价值不是“收藏更多网页”，而是同时降低四种成本：

1. 持续发现和获取信息的成本；
2. 判断信息是否值得关注的成本；
3. 将信息整理为长期知识的成本；
4. 在需要时重新查询、核对和分发知识的成本。

### 产品边界

它是：

- 私有、单用户优先的在线信息与知识服务；
- 以来源快照和证据锚点为可信基础的 AI 工作流；
- 可被网页端、客户端、本地项目和消息机器人共同使用的信息中枢。

它不是：

- 不保留出处的 AI 摘要流；
- 无限制抓取互联网的通用爬虫；
- 让网页内容直接指挥工具的自治 Agent；
- 首版就支持所有格式和所有消息平台的集成平台；
- 用一个“可靠度分数”自动裁决事实真假的系统。

## 3. 三条核心闭环

### 3.1 持续信息闭环

```text
已知信源/发现规则
  → 定时获取
  → 保存来源快照
  → 解析、去重与变化检测
  → AI 筛选、总结、抽取和关联
  → 候选池
  → 日报/周报或即时提醒
  → 用户反馈与规则调整
```

### 3.2 知识沉淀闭环

```text
候选信息
  → 证据检查
  → 一键批准 / 编辑后批准 / 规则自动批准 / 拒绝
  → 原子知识、对象、事件和关系
  → 知识树与时间线视图
  → 后续新信息补充、冲突或更新
```

### 3.3 查询与联动闭环

```text
用户或外部项目提出问题
  → 选择本地知识 / 实时网络 / 混合范围
  → 检索、必要时在线获取并保存临时证据
  → AI 综合并逐项引用来源
  → 返回网页、HTTP、WebSocket 或推送渠道
  → 有价值的在线结果可再次进入候选池
```

## 4. 首个用户与使用场景假设

首版仍以单个用户为目标，用户需要长期跟踪一个专业领域，并已拥有可运行的本地项目或 QQbot。候选场景是：

1. 用户配置若干自己选择的网页、RSS 或 API 信源；
2. 系统每天获取新内容，去重后生成有出处的日报；
3. 用户从日报中一键批准值得长期保存的知识；
4. 用户以后可按知识节点、时间或自然语言找回内容；
5. 日报和事件通过通用集成接口交给现有 QQbot 推送。

具体领域、前三个信源和最有价值的日报内容仍需用户提供真实样本后确认。

## 5. 功能需求

### 5.1 信源、采集与快照

系统需要：

- 管理用户手工添加的网页、RSS/Atom、API、文件或文本来源；
- 为每个订阅信源保存抓取频率、用户时区、启停状态和最后成功游标；
- 对抓取任务记录开始、完成、失败、重试和结果数量；
- 使用内容哈希、来源标识和发布时间等信息避免重复处理；
- 在内容变化时创建新快照，而不是覆盖旧版本；
- 保存规范链接、最终链接、获取时间、发布时间、作者/站点及允许保存的原始内容；
- 在无法保存完整网页时，至少保留可核验的引用片段、必要元数据和内容哈希；
- 遵守站点授权、访问限制、频率限制和内容使用边界，不绕过登录或反爬措施。

自动发现分级开放：

| 等级 | 行为 | 产品阶段 |
| --- | --- | --- |
| L0 | 用户手工粘贴、上传或提交 URL | 最早支持 |
| L1 | 定时读取用户明确订阅的信源 | 候选 MVP |
| L2 | 在用户指定主题、站点或查询范围内发现候选信源/内容；新信源默认需确认后订阅 | 信噪比验证后 |
| L3 | 系统自主扩展来源并探索开放网络 | 远期，不作为默认能力 |

### 5.2 AI 主动加工

AI 可以参与：

- 内容清洗、分段和语言识别；
- 标题与摘要生成；
- 主题、实体、事件、关键陈述和关系候选提取；
- 与历史知识的重复、补充、冲突和相关性判断；
- 变化摘要、日报/周报编排和个性化排序；
- 本地/在线混合查询规划与带证据回答；
- 在限定范围内提出新信源和跟踪建议。

每次 AI 加工必须记录：输入快照或知识版本、输出、时间、模型/规则版本、审核状态和错误。AI 生成内容不能只链接网页首页，必须能追溯到实际输入片段或输入集合。

外部网页、文档和消息一律视为不可信数据，不能借其中的文字改变系统规则、扩大工具权限或触发未授权操作。

### 5.3 入库自动化与权限等级

“自动整理”和“正式入库”是不同权限。建议采用三级入库策略：

| 等级 | 行为 | 适用条件 |
| --- | --- | --- |
| A0 候选 | AI 自动加工后进入候选池 | 默认模式 |
| A1 一键入库 | 用户在网页、日报或 QQbot 中明确批准 | 候选 MVP |
| A2 规则入库 | 命中白名单信源、内容类型、阈值和数量上限后自动批准 | 经过试运行验证后 |

A2 必须支持冲突转人工、每日上限、审计记录和限期回滚。实体合并、覆盖用户知识、删除以及向外部系统执行高影响操作，不因置信度高而自动进行。

### 5.4 可信度与来源说明

每条来源型知识、AI 总结和查询答案都应展示可点击出处。系统不得把下列维度压成一个含义模糊的“真值分数”：

| 维度 | 回答的问题 |
| --- | --- |
| 可追溯性 | 能否回到当时的来源快照和准确片段？ |
| 来源评价 | 该站点、作者或机构在此领域是否值得信赖？ |
| 解析/抽取置信度 | 系统是否正确读取了文本、图片或实体？ |
| 关联置信度 | 提到的对象是否真是知识库中的同一对象？ |
| 交叉印证 | 是否有独立来源支持、补充或反驳？ |
| 新鲜度 | 证据和结论距当前时间多久，是否可能过期？ |
| 审核状态 | 待审核、用户确认、有争议、已驳回或已撤回？ |

“用户确认”只表示用户接受该记录或确认来源确实这样声称，不自动等于客观事实为真。

任何来源评价都必须记录评价维度、适用领域/范围、评价者、依据和评价时间；“某来源在某领域通常可靠”不能自动传递成“该来源的每条陈述都正确”。

### 5.5 知识组织

系统需要支持：

- 实体、概念、来源陈述、AI 总结、AI 推断、用户笔记和事件等不同知识种类；
- 稳定 ID、别名、版本、关系和撤回状态；
- 同一事实的不同来源与相互冲突的陈述并存；
- 从知识返回来源，也能从来源查看产生的知识；
- 把同一知识放入多个知识树位置而不复制正文；
- 用类型化关系表达语义，不用文件夹或标签冒充所有关系。

知识树只是组织和导航视图，不是唯一的数据真相：树中的父子关系不自动等于 `is_a` 或 `part_of`。

每个知识修订需要保存不可混淆的认知角色 `epistemic_role`，例如：原文摘录、来源声称、派生总结、系统推断或用户断言；同时单独记录归属来源 `attributed_to` 与审核状态。批准 AI 总结只改变其审核状态，不能把它变成“来源原话”或“已证实事实”。

引用必须绑定到具体知识修订，而不是只绑定稳定知识 ID。摘要或陈述被编辑后，旧引用只能在重新核验后显式继承；语义已经变化时应创建新修订或新知识。

### 5.6 时间线

时间线至少需要区分：

- `published_at`：来源发布时间；
- `captured_at`：系统获取时间；
- `event_time`：内容所描述事件发生的时间；
- `valid_from / valid_to`：某项知识的适用时间；
- `created_at / updated_at`：知识入库和编辑时间。

默认时间线优先使用事件时间；无法确定时回退到发布时间，并明确显示所用时间类型。网页更新只表示出现新快照，不直接证明旧知识失效或错误。

时间值需要记录时区、精度以及是否由 AI 推断。发布时间只能作为显示回退，不能被写成事件时间。

### 5.7 本地、在线与混合查询

查询必须允许用户明确选择范围：

- **本地知识**：已经正式进入 StruInfo 的私人知识；
- **实时在线**：当前从网络获取、尚未正式入库的临时资料；
- **混合查询**：先利用私人知识，再用在线资料补充新信息。

结果界面必须区分本地快照与实时在线结果，显示快照年龄和获取时间。实时结果只有在保存来源快照、证据片段和获取时间后，才能进入候选池或正式知识库。

自然语言回答中的重要结论必须带引用；证据不足时应明确说“不足以判断”，并将 AI 推断与来源陈述分开呈现。

本文暂时把“本地知识”解释为存放在 StruInfo 私有知识库、区别于互联网即时结果的内容。如果它必须只保存在用户设备且不能上传云端，则需要本地桥接与联邦检索，这是会改变系统边界的待确认需求。

### 5.8 日报、周报与提醒

报告需要支持：

- 用户时区、发送时间、统计窗口、主题和信源范围；
- 新颖度与重复项过滤；
- 按主题、对象或事件聚合，而不是简单拼接摘要；
- 每个报告项包含摘要、相关原因、出处、已有知识关联和操作入口；
- 一键入库、编辑后入库、忽略一次、屏蔽相似主题和调整信源权重；
- 推送失败重试、投递记录、静默时段和幂等处理；
- 周报基于一周信息重新综合，而不是机械合并七份日报。

日报/周报同时是信息输出和候选审核入口。

### 5.9 外部项目与 QQbot 联动

知识库核心不包含 QQ 平台专属逻辑。QQbot 是一个薄适配器，通过通用接口获得摘要、链接和候选项，并转发明确的批准或查询命令。

接口职责建议为：

- HTTP：提交资料、创建信源、查询任务、搜索知识、批准/拒绝和管理规则；
- WebSocket：展示处理进度和即时界面更新；
- Webhook：可靠通知 `candidate.ready`、`digest.ready`、`ingest.completed`、`ingest.failed`、`knowledge.updated` 等事件。

所有可能被外部系统重试的写操作必须支持幂等键；异步操作返回任务 ID；WebSocket 断开后仍能通过 HTTP 恢复最终状态；Webhook 采用至少一次投递，事件包含事件 ID、时间戳、资源 ID 和版本，并支持签名、重试和接收方去重。

QQ 中的普通自然语言不能直接执行批量批准、合并、删除等高权限操作。QQ 身份需要绑定到 StruInfo 用户/工作区，敏感正文应通过受控链接查看。

### 5.10 在线与云端运行

首版按单用户私有服务设计，但从一开始保留：

- 稳定资源 ID 和工作区 ID，不把本机绝对路径作为业务标识；
- 长任务可恢复、可重试且幂等；
- API 和事件版本；
- 配置、密钥与业务数据分离；
- 附件通过逻辑资源 ID 引用；
- 数据删除、导出、备份和恢复能力；
- 模型调用范围、费用、延迟与数据外发边界可配置。

若未来云端服务需要与本地服务器、目录或客户端通信，应由本地桥接程序主动建立受认证的出站连接，只暴露用户明确授权的能力和目录；不要求用户把局域网服务直接开放到公网。

## 6. 候选最小数据语义

以下是需求层对象，不代表已经选定数据库：

| 对象 | 职责 |
| --- | --- |
| `Watch / Endpoint` | 用户订阅或提交的入口，如 RSS、API、网页栏目、本地目录或手工输入 |
| `FetchRun` | 对一个入口的单次获取；记录游标、结果、错误和重试 |
| `Resource` | 一篇文章、一条 API 记录或一个文件等可独立引用的内容；一个 RSS 获取可产生多个 Resource |
| `Snapshot` | 某个 Resource 在某次获取时的不可变版本；URL 会变化，快照才是证据 |
| `Fragment` | 快照中的准确位置，如字符区间、DOM 区域、页码或图片区域 |
| `Candidate` | AI 处理后尚未正式入库的信息、关系或更新建议 |
| `KnowledgeItem / Revision` | 有稳定 ID 和不可变修订的实体、陈述、总结、推断、笔记或事件 |
| `Citation` | 某个具体 Knowledge Revision 对原始 Fragment 的直接引用 |
| `Derivation` | 某个具体总结/推断修订由哪些 Fragment、Knowledge Revision 或处理运行加工而来 |
| `Relation` | 知识之间有方向、有类型且有审核状态的关系 |
| `TreePlacement` | 知识在一个或多个树视图中的位置，不复制知识本身 |
| `Assessment` | 对入口、内容、知识修订或关系的分维度评价；记录范围、评价者、依据和生效时间 |
| `Digest / Delivery` | 报告内容、统计窗口、发送渠道、状态和幂等记录 |
| `Integration / Event` | 外部系统凭据范围、订阅事件和投递状态 |

必须保持的语义边界：

- 网页链接不等于网页快照；
- 原文摘录不等于来源陈述，来源陈述不等于 AI 总结，AI 总结不等于 AI 推断；
- 来源版本不等于知识版本；
- 在线搜索结果不等于已入库知识；
- 知识树父子关系不等于事实关系；
- 发布时间、事件时间、抓取时间和入库时间不能混用。

内容变化检测需要同时区分原始响应哈希与规范正文哈希，避免广告或版式变化制造大量假更新。发现新 Snapshot 后，应先生成差异/更新候选，标记受影响的总结“待复核”或“可能过期”，再产生新的 Knowledge Revision；不得静默改写或撤销既有知识。

## 7. 最早价值验证与候选第一版

知识树、时间线、混合问答和外部项目平台都是已声明的产品需求，但不应全部成为首次价值验证的前置条件。

### 7.1 MVP-0：一个信源的价值探针

先验证最薄闭环：

> 一个已知信源 → 保存快照 → AI 生成带出处摘要 → 最简日报 → 用户批准 → 在已保存列表中找回并回看原文。

只包含：

- 单用户、本机回环地址上的浏览器界面；
- 一个手工配置的公开信源，优先 RSS/Atom；
- 一次手工触发或固定每日获取；
- Resource、Snapshot、Fragment 和基本去重；
- AI 标题、摘要、相关原因及证据引用；
- 最简候选日报、批准、拒绝和纠错；
- 已保存列表、关键词找回和原文回看；
- 基本状态、错误记录和批准幂等。

暂不要求知识树、时间线、语义问答、周报、自动发现、Webhook 或云部署。它们不会被取消，但要由真实找回与判断任务决定进入顺序。

### 7.2 MVP-1：已知信源到主动推送

MVP-0 显示真实价值后，再形成第一条可日常使用的纵向切片：

> 两个已知信源 → 稳定定时获取 → AI 去重、总结和关联 → 可追溯日报 → Webhook 推送 → 登录网页一键批准 → 可查询的私人知识。

候选增量包括：

- 可恢复的每日调度、游标、重试和变化检测；
- 两个真实信源及候选池；
- 主题/实体/关键陈述和已有知识关联建议；
- 通用、版本化 HTTP API 与至少一次投递的 Webhook；
- QQbot 只负责展示摘要和已登录网页链接，不直接执行写操作；
- 基础搜索与 JSON 数据导出；
- 根据阶段 0 的真实任务，选择加入知识树、时间线或带出处本地问答中的最小必要部分。

候选第一版暂不包含：

- 开放网络自主发现；
- 无人审核的规则自动入库；
- 任意网页、登录态页面和复杂反爬站点；
- 完整图片理解、音频和视频；
- 大型知识图谱画布和复杂本体；
- 多用户协作和多租户商业化；
- StruInfo 内部直接实现 QQ 协议；
- QQbot 未经身份绑定直接批准或修改知识；
- 云端直接访问用户局域网；
- 让网页内容触发任意工具或代码执行。

## 8. 验收场景

### 8.1 MVP-0 验收

1. 用户配置一个真实信源，系统获得 5–10 条内容并保存可核验快照。
2. 每个摘要的重要陈述都能返回准确来源片段；证据不足的内容明确标注。
3. 日报能帮助用户更快决定“保存、忽略或稍后处理”，而不是增加审核负担。
4. 用户批准一项后，可在已保存列表中找回并回看原文；重复批准不会重复入库。
5. 用户可以纠正摘要，且修改后的内容不会继续冒用不支持它的旧引用。
6. 用户愿意让系统继续处理下一批内容，且至少一个首要指标优于当前做法。

### 8.2 MVP-1 验收

1. 用户订阅两个已知信源，并设置每天 08:00 获取。
2. 新出现三条内容，其中一条与历史内容重复；系统仅产生两个新候选并解释判断。
3. 日报中的每项都有摘要、相关原因、来源链接/快照和建议关联。
4. Webhook 可能以同一事件 ID 投递多次，但 QQbot 只展示一次；接收失败后可重试并保留尝试记录。
5. QQbot 中的链接打开已登录网页；用户批准后，即使重复点击也只入库一次。
6. 入库知识能够返回准确证据，并能通过阶段 0 选定的找回方式定位。
7. 抓取、AI 或推送失败有独立且明确的状态，不会被一个“已完成”掩盖。
8. 用户能够纠错，并导出来源、知识和引用映射。

## 9. 非功能与安全要求

- 抓取任意 URL 时防止 SSRF：禁止访问未授权的本机、内网和云元数据地址，并限制跳转、大小、类型和超时；
- 外部内容只作为数据，防止提示注入改变系统指令或工具权限；
- 抓取、生成报告、批准和入库应支持幂等；事件允许至少一次投递，但重复事件不得产生重复副作用；
- 密钥不出现在报告、消息正文或普通日志中；
- 所有外部写入与推送具有身份、范围和审计记录；
- 设置抓取并发、频率、深度、日报条数和 AI 预算上限；
- 支持来源与知识删除、保留期限、导出和备份；
- 本地服务默认只监听回环地址；所有写接口仍需认证及浏览器侧 CSRF 防护，监听非本机地址必须显式开启；
- 公网在线模式必须提供认证、传输加密和私有默认可见性；
- 本地桥接只能执行能力级授权操作，不提供通用命令执行；目录授权需防止路径规范化或符号链接绕过；
- 任何自动化都能暂停、解释和回滚。

## 10. 进入实现前仍需确认

1. 第一个长期跟踪的具体领域是什么？
2. 最先接入的一个主要信源和一个备选信源是什么，属于 RSS、普通网页、API 还是其他形式？
3. 理想日报需要回答什么问题；什么内容只需阅读，什么内容值得正式入库？
4. “本地知识”是指 StruInfo 私有数据库，还是必须只存在用户设备、不可上传的资料？
5. 第一条推送链路是通用 Webhook 接现有 QQbot，还是 QQbot 主动调用 StruInfo API？
6. AI 默认应当“自动分析 + 一键批准”，还是某些白名单信源从第一天起就允许规则自动入库？
7. 哪些内容允许发送给外部 AI 模型，哪些必须使用本地模型或完全不处理？
8. 来源快照需要保存全文、页面截图、主要正文，还是只保存引用片段？
9. 云端部署是首版验收要求，还是核心闭环稳定后的迁移目标？

在前五项未确认前，不锁定最终 MVP、抓取方案、消息协议细节或部署架构。

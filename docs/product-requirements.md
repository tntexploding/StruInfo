# StruInfo 产品需求

- 状态：M1D-2 文档标签聚合与 Document ↔ Entry 导航已实现；正式知识保留为可选深化层
- 最近更新：2026-08-21
- 目的：定义“来源可追溯、AI 可增强且无 AI 仍完整可用的个人知识摄取与维护系统”的产品边界和首个验证切片
- 历史基线：[产品需求 v0.1](archive/product-requirements-v0.1.md)
- 文档条目处理细则：[文档条目处理准则](document-entry-processing-guidelines.md)

## 1. 方向演进

v0.1 将 StruInfo 定义为可追溯的知识结构化工作台。

v0.2 将产品扩展为持续采集外部信息、由 AI 主动加工、形成可核验知识、支持本地与在线查询，并能向用户或其他项目推送结果的个人信息枢纽。

当前基线进一步明确：**知识摄取与维护是产品内核，日报、QQbot、公共 API 和云端部署是建立在内核之上的后续交互与运行形态。** 首版首先验证异构资料能否被保存、筛选、结构化、关联、维护和找回，而不是先验证推送渠道。

## 2. 产品定义

### 一句话定位

> StruInfo 是一个来源可追溯、AI 可增强的个人知识摄取与维护系统：它保存指定信源或手工资料的原始证据，通过用户操作、确定性规则或 AI 提案拆分、比较、关联、重组和维护版本化知识，并通过网页提供审核、接管、浏览和带出处检索。AI 不可用时，核心知识操作与搜索仍然成立。

长期形态仍是可在线使用的个人信息枢纽，可以加入定时采集、实时网络查询、知识树、时间线、报告、外部项目接口和消息推送；这些能力不再定义首个核心闭环。

本文中的“在线”需要区分三层：

1. **能够按策略访问互联网信源和核验来源**：核心能力；
2. **通过浏览器使用**：首个产品切片，初期只需在本机或受控局域网访问；
3. **由公网云服务器托管**：核心逻辑稳定后的部署目标。

### 核心任务

> 当我面对周刊、论文、项目文档、设计大纲、教程、评论文章或其他资料时，我希望系统完整保留可用证据，并允许我或确定性工具把资料分类、拆分、连接和重组为长期知识。AI 可以自动提出合适粒度、与既有内容比较并建立联系，但不会拥有另一套数据库语义。系统应在发现重复、补充、冲突或结构问题时可解释地维护知识，并在我查询时结合来源、关系、版本和时间返回结果；随着反馈积累，AI 可以逐步接管低风险工作，但我始终拥有最高权限的手工操作、暂停、纠错、撤回和重处理入口。

### 核心价值

StruInfo 的价值不是“收藏更多网页”，而是降低五种成本：

1. 获取和保存异构资料及其来源证据的成本；
2. 判断信息量、趣味性、探索价值和噪声的成本；
3. 将资料拆分、合并和组织为长期知识的成本；
4. 发现重复、冲突、过期内容和结构缺口的成本；
5. 重新查询、核验、更新和复用知识的成本。

系统还要主动抵抗单纯偏好学习造成的信息茧房：既学习用户当前关心什么，也保留独立、可配置的探索策略，用邻域扩展、跨领域连接、基础缺口、新兴信号和观点多样性拓宽知识面。

### 产品边界

它是：

- 私有、单用户优先的知识摄取、维护与检索工作区；
- 以来源快照、文档结构和证据锚点为可信基础的 AI 工作流；
- 同时保留原始资料、文档结构、正式知识和控制记录的分层系统；
- 在不配置 AI、Embedding 或外部模型时仍可完整导入、分类、编辑、关联、重组、检索和导出；
- 能够在用户或版本化策略授权范围内逐步提高自动化程度的系统。

它不是：

- 不保留出处的 AI 摘要流；
- 只把文档切成向量块的问答外壳；
- 无限制抓取互联网的通用爬虫；
- 让网页内容或模型输出直接指挥工具、扩大权限或修改数据库的自治 Agent；
- 强迫论文、周刊、项目文档和框架教程采用同一种知识粒度的系统；
- 以点击率、既有偏好匹配率或单一“真值/兴趣分数”优化全部行为的推荐系统；
- 首版就支持所有格式、全部媒体理解和所有消息平台的集成平台。

## 3. 三条核心闭环

### 3.1 资料摄取与价值判断闭环

```text
指定信源 / 手工上传
  → 保存原始版本、来源和媒体
  → 解析文档结构与独立内容单元
  → 分维度评估信息价值、兴趣、探索价值和噪声
  → 完整处理 / 拆分处理 / 压缩处理 / 仅保留来源 / 忽略 / 人工判断
  → 记录用户反馈并形成版本化偏好规则
```

### 3.2 知识形成与维护闭环

```text
已保存的资料或内容单元
  → 按结构生成可追溯 InformationEntry
  → 用户 / 确定性规则 / AI 提案标注内容、类型和领域关键词
  → 聚合文档标签并建立选择性关联
  → 按需深化为对象、概念、观点、事件、方法、资源和正式关系
  → 与既有知识比较
  → 新增 / 修订 / 关联 / 记录冲突 / 请求人工处理
  → 由用户决定或版本化策略授权正式知识用例提交
  → 保留变更集、引用、派生、规则版本和回滚路径
```

模型供应商适配器不能直接写正式知识。自动入库表示应用根据用户批准的策略调用正式知识用例，不表示模型绕过权限、校验和审计写数据库。

### 3.3 查询、反馈与后续联动闭环

```text
用户在网页提出结构化搜索或问题
  → 选择私人知识 / 实时网络 / 混合范围
  → 从知识、关系、证据、来源和时间维度检索
  → 必要时在允许范围内获取新的网络证据
  → 返回可解释的记录；启用 AI 时可进一步综合并逐项引用来源
  → 用户纠错、接管或要求重新处理
  → 反馈进入偏好、探索和知识维护记录
```

日报、周报、HTTP/WS、Webhook、QQbot 和其他客户端是该闭环的后续入口或出口，不改变知识库核心的权限和证据规则。

## 4. 首个用户与已确认场景

首版面向单个用户，通过本机浏览器验证资料入库、审核、知识浏览和搜索。

首个真实信源确定为[阮一峰《科技爱好者周刊》GitHub 仓库](https://github.com/ruanyf/weekly)：

1. 以仓库中的原始 Markdown 周刊文件作为主要输入；
2. 记录仓库、分支、路径、Git commit、内容哈希、期数、发布时间和获取时间；
3. 以栏目中的独立条目作为主要人工筛选单位，同时保留整期文档结构；
4. 首版记录条目中的外部链接，但不批量抓取全部二级来源；
5. 图片先保存或引用允许保存的原始版本，关联所在内容，并标注封面、解释图、数据图、截图、示例、装饰或未知用途；
6. 先由用户标记处理结果，积累样本后由 AI 提议可读、版本化的筛选规则；
7. 通过筛选的内容可以由用户或确定性规则拆分、比较和关联；AI 随后通过相同的变更提案边界自动增强，低风险新增和非破坏性更新可按策略提交，高影响操作转人工；
8. 第一阶段只要求网页端完成核心验证，报告、QQbot 和外部项目接口后移。

周刊 Markdown 是首版实际捕获和引用的直接来源。条目指向的外部页面是“来源所引用的二级来源”；在系统尚未获取并保存该页面前，不能把周刊的转述冒充为外部页面原文，也不能声称已核验二级来源。

首批至少选择 10 期历史周刊，并对其中的独立条目建立人工标注集。仓库公开可读或自称“开源”不自动等于获得任意保存和再分发权；正式保存全文、图片或公开部署前仍需记录来源授权、保留范围和再分发边界。

## 5. 功能需求

### 5.1 信源、采集与快照

系统需要：

- 管理用户手工添加的 Git 仓库路径、网页、RSS/Atom、API、文件或文本来源；
- 为每个订阅信源保存抓取频率、用户时区、启停状态和最后成功游标；
- 对抓取任务记录开始、完成、失败、重试和结果数量；
- 使用内容哈希、来源标识和发布时间等信息避免重复处理；
- 在内容变化时创建新快照，而不是覆盖旧版本；
- 保存规范链接、最终链接、获取时间、发布时间、作者/站点及允许保存的原始内容；
- 对 Git 来源保存仓库、ref、提交身份、路径和原始文件哈希，不只保存随时间变化的分支 URL；
- 在无法保存完整网页时，至少保留可核验的引用片段、必要元数据和内容哈希；
- 区分“允许获取这个信源”“这份资料值得处理”和“允许提交哪些知识变更”，不能用一个开关代表全部授权；
- 遵守站点授权、访问限制、频率限制、保留期限和内容使用边界，不绕过登录或反爬措施。

自动发现分级开放：

| 等级 | 行为 | 产品阶段 |
| --- | --- | --- |
| L0 | 用户手工粘贴、上传或提交 URL | 最早支持 |
| L1 | 定时读取用户明确订阅的 Git、RSS、API 或网页信源 | 核心逻辑验证后 |
| L2 | 在用户指定主题、站点或查询范围内发现候选信源/内容；新信源默认需确认后订阅 | 信噪比验证后 |
| L3 | 系统自主扩展来源并探索开放网络 | 远期，不作为默认能力 |

### 5.2 异构文档与分层保存

系统不要求所有来源采用相同格式或相同知识粒度，而是保持五个可相互追溯的层次：

| 层级 | 职责 |
| --- | --- |
| 证据层 | 保存允许保留的原始字节、来源、版本、哈希、媒体和捕获时间 |
| 文档层 | 保存文档、章节、段落、列表项、表格、图片位置和原有顺序 |
| 条目层 | 保存绑定具体 Snapshot 的 InformationEntry、三维关键词、文档标签和选择性关联；是普通浏览与检索主单元 |
| 知识层 | 保存对象、概念、断言、事件、方法、框架、关系和不可变修订 |
| 控制层 | 保存准入决定、价值评估、偏好规则、探索策略、处理计划、变更集、冲突和人工接管记录 |

处理者需要先使用与资料类型匹配的处理计划，而不是无条件把全文切成同样大小的片段。计划可以由用户、确定性解析器、规则或 AI 提出：

- 周刊或汇总文章通常按栏目和独立条目筛选、拆分；
- 论文保留全文结构，同时提取研究对象、方法、条件、数据和结论；
- 项目文档与设计大纲保留文档版本和决策上下文；
- 架构教程或全新领域可以形成全文级“框架知识”，再按实际价值拆出内部结构；
- 广告、修辞或重复介绍可以压缩成少量条目，也可以只保留来源记录或忽略；
- 无法可靠拆分的资料可以作为全文级知识对象保存，不伪造原子结构。

人工审核中的“完整处理 / 拆分 / 压缩”是当时的处理倾向和审计事实，不是对后续知识形状的强制命令。确定性处理器必须同时检查正文长度、可辨认结构、媒体用途和用户词表规则：很短的独立条目通常形成一个知识项，即使审核时选择过拆分或压缩；只有长度和内部结构都足够时才真正拆分。用户仍可在知识变更提交前覆盖该计划。

结构化结果出错时，用户必须能够返回原始资料、查看处理计划并重新处理。

用户在录入时可以把一份资料标记为**隐私文档**。该标记具有以下首版语义：

- 无论后续是否拆分，系统都同时保存原始字节和完整规范化全文；两者位于包体外工作区 Blob 存储，PostgreSQL 保存内容身份、结构和隐私事实；
- 由隐私文档的 Fragment 创建或派生的知识修订自动成为隐私条目；后续普通修订不得隐式解除隐私；
- 关系自身使用隐私证据，或任一当前端点为隐私条目时，该关系按隐私关系处理；公共条目与隐私条目之间的连接也不例外；
- 普通搜索、来源回看和关系查询默认排除这些内容。只有用户在本次操作中明确勾选“查询隐私文档”或“查看隐私文档”，才返回隐私条目、相关关系或完整文档；
- 隐私文档全文以单独的文档结果展示，不能因已经拆成条目而丢失整体语境。

该标记是单用户工作区中的内容可见范围，不冒充加密、身份认证或多用户访问控制。公开部署前仍需完成独立认证与加密边界。

### 5.3 信息价值、偏好与探索

系统不得把内容价值、用户兴趣、探索作用和证据可靠性压成一个分数。至少分别记录：

| 维度 | 回答的问题 |
| --- | --- |
| 信息密度 | 有效事实、方法或观点相对于冗余内容的比例如何？ |
| 广度 | 内容覆盖多少对象、概念、领域或关系？ |
| 深度 | 是否提供机制、条件、数据、推导或可复用解释？ |
| 新颖性 | 相对于已有知识增加、修正或挑战了什么？ |
| 当前兴趣 | 是否直接匹配用户当前关注方向？ |
| 邻域扩展 | 是否能从已有兴趣自然扩展到相邻主题？ |
| 跨领域连接 | 是否能在原本分离的知识之间形成有意义联系？ |
| 基础缺口 | 是否补足已有结构所依赖但缺失的基础知识？ |
| 新兴信号 | 是否可能具有尚未形成稳定关联的长期价值？ |
| 观点与来源多样性 | 是否提供不同立场、方法、地域、学科或来源？ |
| 偶然发现价值 | 是否虽然不直接相关，但足够新奇或有启发性？ |
| 噪声/营销强度 | 是否以广告、地位评价、修辞、重复或强引导性内容为主？ |
| 认知成本 | 理解和验证它需要多少背景、时间和外部资料？ |

系统分别作出两类决定：

- **知识准入**：完整处理、拆分处理、压缩处理、仅保留来源、忽略或待人工判断；
- **注意力分配**：安静入库、普通展示、探索推荐、优先审核或不主动展示。

高信息价值但低当前兴趣的内容可以安静入库；高探索价值的陌生内容可以进入探索区域；只匹配既有兴趣但内容空洞的资料不得因此入库。

系统需要分开保存：

- `PreferenceProfile`：从用户行为中总结当前偏好；
- `ExplorationPolicy`：规定如何主动突破已有偏好，不能被普通点击、忽略或拒绝行为自动覆盖。

人工反馈不能只有“通过/不通过”，应允许区分：已经知道、内容质量低、来源不可靠、暂时不需要、确实不感兴趣、陌生但值得探索、推荐方向正确但样本不合适。AI 提议的规则必须可读、版本化、可试运行，并说明使用了哪些反馈样本。

### 5.4 AI 主动加工

AI 可以参与：

- 内容清洗、分段和语言识别；
- 文档类型判断和处理计划生成；
- 标题、摘要以及压缩条目生成；
- 对象、概念、事件、方法、框架、关键陈述和关系提取；
- 与历史知识的重复、补充、冲突、过期和结构缺口判断；
- 生成新增、修订、关联、冲突或人工处理的知识变更提案；
- 在允许的站点和预算内搜索冲突证据，并保存实际使用的页面和片段；
- 从人工反馈总结偏好规则和探索建议；
- 本地/在线混合查询规划与带证据回答；
- 在限定范围内提出新信源、跟踪建议以及后续报告编排。

每次 AI 加工必须记录：输入快照或知识版本、处理计划、输出、时间、供应商、模型、提示/规则版本、参数、用量、审核或策略授权状态、警告和错误。AI 生成内容不能只链接网页首页，必须能追溯到实际输入片段或输入集合。

外部网页、文档和消息一律视为不可信数据，不能借其中的文字改变系统规则、扩大工具权限或触发未授权操作。

#### 5.4.1 无 AI 基线

AI 是可替换的生产力适配器，不是数据库或核心工作流的运行依赖。未配置 AI Provider、Embedding Provider 或模型凭据时，系统必须支持：

- 手工输入、文件导入和 Markdown 等确定性结构解析；
- 用户自定义内容分类、准入动作和知识类型；
- 手工选区拆分、创建/修订知识、添加别名和类型化关系；
- 集合、框架、树位置、时间线和保存查询；
- 重复、冲突、撤回、合并审核、补偿修订和重新处理；
- 中文子串、别名、结构化过滤、来源、时间和关系检索；
- 版本化导入/导出、备份和恢复。

系统不能把“AI 未启用”显示为知识库故障。AI 处理器只返回标准变更提案，并与用户、规则和导入器共享同一个知识命令、权限、引用、版本和审计边界。

### 5.5 入库自动化与权限等级

“模型生成内容”“应用自动处理”和“正式知识变更”是不同权限。自动化按以下阶段逐步开放：

| 等级 | 行为 | 适用阶段 |
| --- | --- | --- |
| A0 人工操作 | 用户决定内容单元的处理结果并可手工完成知识变更；AI 若启用则负责解释、拆分和提出变更 | 首批样本 |
| A1 范围授权 | 用户批准资料或内容单元后，应用允许 AI 结果自动提交低风险新增和非破坏性修订 | 首个知识闭环 |
| A2 自动分流 | 高确定性内容自动处理，低价值内容自动忽略，不确定内容进入人工审核 | 规则试运行通过后 |
| A3 委托维护 | AI 按版本化策略主动补充关系、修订局部结构和处理更新 | 长期反馈稳定后 |

正式知识只能由 `knowledge` 应用用例创建或修订。授权来源可以是本次用户命令，也可以是用户已经启用的策略版本；模型适配器、来源适配器和后台任务都不能绕过该入口直接改表。

A1 及以上必须支持范围、有效期、试运行、数量/费用上限、冲突转人工、暂停、审计、补偿修订和重新处理。用户始终可以查看“为什么自动处理”、接管待处理任务、禁用规则并撤回规则造成的知识变更。

以下操作默认保持人工确认，不因置信度高而自动进行：合并两个既有核心词条、删除或彻底替换知识、裁决重要冲突、大规模重排结构、扩大信源/工具权限，以及把私人内容发送给新的外部服务。

### 5.6 可信度与来源说明

每条来源型知识、AI 总结和查询答案都应展示可点击出处。系统不得把下列维度压成一个含义模糊的“真值分数”：

| 维度 | 回答的问题 |
| --- | --- |
| 可追溯性 | 能否回到当时的来源快照和准确片段？ |
| 来源评价 | 该站点、作者或机构在此领域是否值得信赖？ |
| 解析/抽取置信度 | 系统是否正确读取了文本、图片或实体？ |
| 关联置信度 | 提到的对象是否真是知识库中的同一对象？ |
| 交叉印证 | 是否有独立来源支持、补充或反驳？ |
| 新鲜度 | 证据和结论距当前时间多久，是否可能过期？ |
| 审核状态 | 待审核、用户确认、有争议、已驳回或已撤回？ |

“用户确认”只表示用户接受该记录或确认来源确实这样声称，不自动等于客观事实为真。

任何来源评价都必须记录评价维度、适用领域/范围、评价者、依据和评价时间；“某来源在某领域通常可靠”不能自动传递成“该来源的每条陈述都正确”。

信息价值、兴趣和探索评分不属于事实可靠性。界面和排序不得用“用户感兴趣”暗示内容更真实，也不得用“来源可靠”暗示内容一定值得向用户主动展示。

### 5.7 知识组织

[知识核心架构](knowledge-core-architecture.md)定义数据库的规范模型。系统使用有证据、可版本化的关系型知识图，而不是把向量、聊天记录、树布局或 AI 摘要当作唯一真相。

普通文档首先形成 `InformationEntry`：它保留 Snapshot、准确来源位置、正文、拆分版本和
内容/类型/领域三类关键词，并作为文档浏览、关键词编辑、关联发现和搜索的主单元。
`KnowledgeItem` 不再是每个短 Fragment 的必经步骤；只有需要稳定语义身份、不可变知识
修订、正式来源陈述或类型化事实关系时，才从 Entry 或其他证据深化为正式知识。
两层可以互相引用，但不能混用身份、状态或关系语义。

以下维度必须分开保存：

- 内容分类，例如小说、论文、教程、广告或工具介绍；
- 准入动作，例如完整处理、拆分、压缩、仅保留来源、忽略或待审核；
- 知识类型，例如实体、概念、断言、事件、方法、框架、资源或作品；
- 认知角色、审核状态和操作来源。

内容分类来自工作区版本化词表，可以由用户扩展；它不能与准入动作或偏好评分共用一个字段。将一份资料归类为“小说”不会自动决定是否完整保存、拆分或忽略。

首个 A0 人工实现由[人工分类与准入合同](manual-curation-contract.md)约束：它只绑定精确 Snapshot/Fragment，保持分类、准入动作和各评级维度独立，不定义综合分、阈值、偏好模型或自动准入。真实词表、标签、备注和评分属于包体外工作区数据，不得成为代码常量、迁移种子或测试样本。

系统需要支持：

- 实体、概念、来源陈述、AI 总结、AI 推断、用户笔记、事件、方法和框架等不同知识种类；
- 既能保存原子断言，也能保存具有整体语义的全文级或框架级知识；
- 稳定 ID、别名、版本、关系和撤回状态；
- 同一事实的不同来源与相互冲突的陈述并存；
- 从知识返回来源，也能从来源查看产生的知识和处理变更集；
- 把同一知识放入多个知识树位置而不复制正文；
- 用类型化关系表达语义，不用文件夹或标签冒充所有关系。

可复用概念与对象特定断言必须分开。例如“耐高温”可以是供多个对象引用的概念，而“对象 D 在 800°C 下工作”是带条件、对象和来源的断言，不能复用为对象 E 的事实。

知识树只是组织和导航视图，不是唯一的数据真相：树中的父子关系不自动等于 `is_a` 或 `part_of`。AI 可以提出局部结构优化，但大规模移动、合并和删除保持人工确认。

每个知识修订需要保存不可混淆的认知角色 `epistemic_role`，例如：原文摘录、来源声称、派生总结、系统推断或用户断言；同时单独记录归属来源 `attributed_to`、AI 来源、授权策略和审核状态。策略自动入库不会把 AI 总结变成“来源原话”或“已证实事实”。

引用必须绑定到具体知识修订，而不是只绑定稳定知识 ID。摘要或陈述被编辑后，旧引用只能在重新核验后显式继承；语义已经变化时应创建新修订或新知识。

### 5.8 冲突核验与知识维护

发现冲突时，系统先区分：真正的事实矛盾、时间变化、适用范围不同、定义/单位/翻译不一致，以及来源陈述与 AI/用户推断不一致。

需要网络核验时，系统应：

- 使用用户允许的站点、主题范围、费用和请求预算；
- 支持按领域配置优先信源，但不把 Wikipedia 或任何单一站点硬编码为所有领域的最终权威；
- 保存搜索词、搜索时间、访问页面、来源快照和实际支持判断的片段；
- 记录 AI 为什么认为冲突已解决、仍然并存或需要人工判断；
- 只有在授权策略允许且不涉及高影响裁决时自动提交修订，否则建立 `ConflictCase` 转人工。

系统不得静默覆盖旧知识。被新证据修正的知识仍保留历史修订、原有依据和替代关系。

### 5.9 时间线

时间线至少需要区分：

- `published_at`：来源发布时间；
- `captured_at`：系统获取时间；
- `event_time`：内容所描述事件发生的时间；
- `valid_from / valid_to`：某项知识的适用时间；
- `created_at / updated_at`：知识入库和编辑时间。

默认时间线优先使用事件时间；无法确定时回退到发布时间，并明确显示所用时间类型。网页更新只表示出现新快照，不直接证明旧知识失效或错误。

时间值需要记录时区、精度以及是否由 AI 推断。发布时间只能作为显示回退，不能被写成事件时间。

### 5.10 本地、在线与混合查询

查询必须允许用户明确选择范围：

- **私人知识**：已经正式进入 StruInfo 的知识及其关系、证据和历史；
- **实时在线**：当前从网络获取、尚未正式入库的临时资料；
- **混合查询**：先利用私人知识，再用在线资料补充或核验。

首个切片先支持对私人知识按关键词、对象、来源、时间、关系和处理状态找回，并允许查看 AI 为什么创建、修订或关联某项知识。

结果界面必须区分私人快照与实时在线结果，显示快照年龄和获取时间。实时结果只有在保存来源快照、证据片段和获取时间后，才能进入待处理变更或正式知识库。

自然语言回答中的重要结论必须带引用；证据不足时应明确说“不足以判断”，并将 AI 推断与来源陈述分开呈现。

本文暂时把“私人知识”解释为存放在 StruInfo 私有知识库、区别于互联网即时结果的内容。外部模型是否能够接收其中的内容仍按工作区显式授权；要求资料只能存在用户设备时，需要本地桥接与联邦检索。

“私人知识库”与用户显式标记的“隐私文档”不是同一个范围：前者指整个本地工作区，后者是在其中额外默认隐藏的内容。普通本地搜索不会因为运行在私人工作区就自动包含隐私文档；每次扩大到该范围都需要明确勾选，并使用与普通搜索不同的分页游标范围。

### 5.11 图片与其他媒体

第一版对图片只要求保存、关联和标注用途，不要求 OCR 或视觉知识提取：

- 保存或引用允许保留的原始图片、来源 URL、内容哈希、类型、尺寸和所在文档位置；
- 关联到文档、内容单元、证据片段或知识条目；
- 用枚举或版本化词表标注封面图、概念解释图、数据图表、操作截图、示例、装饰或未知；
- 区分用途来自原文说明、AI 推断还是用户确认，并为 AI 推断保存置信度；
- 装饰图片不能作为事实证据；图片不可用时仍保留替代文本和来源关系。

后续 OCR、多模态理解、音频和视频必须作为派生处理保留区域或时间锚点，不能覆盖原始媒体。

### 5.12 日报、周报与提醒

报告属于核心知识闭环稳定后的交互入口。后续实现时需要支持：

- 用户时区、发送时间、统计窗口、主题和信源范围；
- 新颖度、重复项、当前兴趣和探索价值的分维度排序；
- 按知识变化、主题、对象或事件聚合，而不是简单拼接摘要；
- 每个报告项包含摘要、展示原因、探索原因、出处、已有知识关联和操作入口；
- 查看知识变更、调整处理规则、忽略一次、降低相似内容展示和转人工审核；
- 推送失败重试、投递记录、静默时段和幂等处理；
- 周报基于一周信息重新综合，而不是机械合并七份日报。

报告可以作为审核或接管入口，但不能成为正式知识唯一入口，也不能把推送成功与知识处理成功混为一个状态。

### 5.13 外部项目与 QQbot 联动

外部接口在核心入库、审核和搜索可用后开发。知识库核心不包含 QQ 平台专属逻辑；QQbot 是薄适配器，通过通用接口获得摘要、链接、查询结果或待处理项。

接口职责建议为：

- HTTP：提交资料、创建信源、查询任务、搜索知识、处理审核和管理规则；
- WebSocket：展示处理进度和即时界面更新；
- Webhook：可靠通知 `review.required`、`ingest.completed`、`ingest.failed`、`knowledge.updated`、`digest.ready` 等事件。

所有可能被外部系统重试的写操作必须支持幂等键；异步操作返回任务 ID；WebSocket 断开后仍能通过 HTTP 恢复最终状态；Webhook 采用至少一次投递，事件包含事件 ID、时间戳、资源 ID 和版本，并支持签名、重试和接收方去重。

QQ 中的普通自然语言不能直接执行批量批准、合并、删除等高权限操作。QQ 身份需要绑定到 StruInfo 用户/工作区，敏感正文应通过受控链接查看。

### 5.14 在线与云端运行

首版按单用户私有服务设计，但从一开始保留：

- 稳定资源 ID 和工作区 ID，不把本机绝对路径作为业务标识；
- 长任务可恢复、可重试且幂等；
- API 和事件版本；
- 配置、密钥与业务数据分离；
- 应用代码、外部运行配置、工作区数据、Blob/导出/备份和秘密存储分别管理；
- 附件通过逻辑资源 ID 引用；
- 数据删除、导出、备份和恢复能力；
- 模型调用范围、费用、延迟与数据外发边界可配置。

所有个人知识、词表、分类、偏好、策略、信源、保存查询、用户提示词、快照、附件、导出和备份必须存放在工作区数据库或源码/安装目录之外的外部数据根。它们不得硬编码、提交到 Git、进入正式 fixture、前端 mock、迁移 seed、构建资源、安装包或容器镜像。

仓库只允许保存配置 schema、没有真实值的示例和合成测试数据。实际运行配置从包体外加载；启动时解析规范绝对路径并拒绝把个人数据根放在 Git 工作树、源码目录、安装目录或容器非持久层内。具体边界由 [ADR 0006](adr/0006-external-configuration-and-personal-data-isolation.md) 固定。

同一应用构建必须能够通过更换包体外运行配置、选择稳定工作区或导入版本化 Workspace Bundle 来切换并重新读取另一套资料、偏好和用户控制数据，不得要求修改源码、重新构建或复制个人资源到 Git。首版允许用受控重启/重新打开实现该能力；候选配置与工作区必须完整验证后才激活，失败不得形成数据库、Blob 和工作区身份的混合状态。

若未来云端服务需要与本地服务器、目录或客户端通信，应由本地桥接程序主动建立受认证的出站连接，只暴露用户明确授权的能力和目录；不要求用户把局域网服务直接开放到公网。

## 6. 候选最小数据语义

以下是需求层对象；PostgreSQL 已确定，具体表和约束以拟议的[知识核心架构](knowledge-core-architecture.md)及后续迁移评审为准：

| 对象 | 职责 |
| --- | --- |
| `Watch / Endpoint` | 用户订阅或提交的入口，如 Git 路径、RSS、API、网页栏目、本地目录或手工输入 |
| `FetchRun` | 对一个入口的单次获取；记录游标、结果、错误和重试 |
| `Resource` | 一篇文章、一条 API 记录或一个文件等可独立引用的内容 |
| `Snapshot` | 某个 Resource 在某次获取时的不可变版本；URL 会变化，快照才是证据 |
| `DocumentNode / Fragment` | 快照中的文档、章节、段落、列表项、字符区间、DOM 区域、页码或图片区域 |
| `MediaAsset / MediaUsage` | 原始媒体身份、所在位置、允许保留的字节或引用，以及封面、解释、图表、截图、示例、装饰或未知用途 |
| `InformationEntry / Revision` | 从具体 Snapshot 形成的首要检索单元；保存稳定身份、顺序、标题路径、正文、证据位置、拆分版本和沿袭 |
| `EntryKeywordAssignment` | 分别保存自由内容关键词、一个类型关键词和一个主领域加最多两个副领域，以及人工/规则/AI 来源 |
| `DocumentTagRevision` | 从全文倾向和 Entry 覆盖率聚合的可修改文档标签及算法版本 |
| `AssociationProjection / Override` | 可重建的相关性分项、基础分和算法版本，以及不会被重算覆盖的人工增强、削弱或屏蔽决定 |
| `VocabularyTerm / ContentClassification` | 工作区自定义内容类别及其版本化指派，例如小说、论文、教程或工具介绍；不决定处理动作 |
| `IntakeDecision` | 对资料或内容单元作出的完整处理、拆分、压缩、仅保留来源、忽略或人工判断动作 |
| `Assessment` | 信息价值、偏好、探索、噪声、来源或抽取等分维度评价；记录类型、范围、评价者、依据和版本 |
| `PreferenceProfile` | 从用户反馈总结出的当前偏好及其样本、规则和版本 |
| `ExplorationPolicy` | 独立于当前偏好的探索类型、预算、展示规则和版本 |
| `ProcessingPlan / Run` | 可选的资料处理策略以及一次确定性/AI/OCR/规则处理的输入、输出、模型、规则、状态和费用 |
| `KnowledgeChangeSet` | 一次处理提出的新增、修订、关联、冲突或人工审核变更，以及授权来源和提交结果 |
| `Candidate` | 尚未获用户或策略授权、存在不确定性或必须人工审核的知识变更 |
| `KnowledgeItem / Revision` | 有稳定 ID 和不可变修订的实体、概念、陈述、总结、推断、笔记、事件、方法或框架 |
| `Citation` | 某个具体 Knowledge Revision 或 Relation Revision 对原始 Fragment 的直接引用 |
| `Derivation` | 某个具体总结/推断修订由哪些 Fragment、Knowledge Revision 或处理运行加工而来 |
| `Relation / Revision` | 具有稳定 ID，并以不可变修订表达端点、方向、类型、限定条件、审核状态和依据的知识关系 |
| `ConflictCase` | 互相矛盾或表面矛盾的知识、证据、分类、网络核验过程和处理状态 |
| `TreePlacement` | 知识在一个或多个树视图中的位置，不复制知识本身 |
| `Collection / SavedView` | 对既有知识的有序组合或保存查询，不复制规范修订 |
| `SearchProjection` | 从当前修订、别名、关系、来源和分类重建的搜索索引；可删除后重建 |
| `AutomationPolicy` | 用户批准的自动化动作、范围、阈值、预算、有效期、版本和暂停状态 |
| `Operation` | 对外可查询的长任务、阶段、进度、错误、尝试和关联资源 |
| `Digest / Delivery` | 报告内容、统计窗口、发送渠道、状态和幂等记录 |
| `Integration / Event` | 外部系统凭据范围、订阅事件和投递状态 |

必须保持的语义边界：

- 网页链接不等于网页快照；
- 直接捕获的周刊来源不等于尚未获取的外部链接来源，转述不等于二级来源原文；
- 整份资料不等于其中每个内容单元都获准进入正式知识；
- 当前兴趣不等于信息价值，探索价值不等于事实可靠性；
- 内容分类不等于处理动作，处理动作不等于知识类型或审核状态；
- 用户批准一份资料不等于授权模型执行合并、删除或冲突裁决；
- 原文摘录不等于来源陈述，来源陈述不等于 AI 总结，AI 总结不等于 AI 推断；
- 来源版本不等于知识版本；
- 在线搜索结果不等于已入库知识；
- AI 变更提案不等于已提交的知识修订；
- 知识树父子关系不等于事实关系；
- 发布时间、事件时间、抓取时间和入库时间不能混用。

内容变化检测需要同时区分原始响应哈希与规范正文哈希，避免广告或版式变化制造大量假更新。发现新 Snapshot 后，应生成差异、受影响知识和 `KnowledgeChangeSet`，标记旧总结“待复核”或“可能过期”；只有得到用户或策略授权后才能提交新修订，不得静默改写或撤销既有知识。

## 7. 最早价值验证与候选第一版

首个验证不以日报或外部接口为中心，而以“资料进入后能否形成正确、可追溯、可维护并能找回的知识”为中心。知识图谱画布、完整时间线、混合在线问答和推送均不作为核心逻辑第一次验收的前置条件。

### 7.1 MVP-0A/0B：来源可追溯的知识摄取核心与 AI 增强

验证闭环：

> MVP-0A：10 期科技周刊 Markdown → 保存来源和版本 → 按结构形成 Entry → 用户编辑三维关键词和选择性关联 → 完成无 AI 搜索与来源回看 → 按需形成版本化正式知识。MVP-0B：AI 在相同 Entry/知识命令边界上提出拆分、标注、比较、关系和查询综合增强。

只包含：

- 单用户、本机回环地址上的浏览器界面；
- 阮一峰科技周刊 GitHub 仓库和至少 10 期固定历史样本；
- 手工导入或固定 fixture，不要求定时监测；
- Resource、Snapshot、DocumentNode、Fragment、MediaAsset 和基本去重；
- 绑定具体 Snapshot 的 InformationEntry、内容/类型/领域关键词、文档标签和可解释的选择性关联；
- 按独立条目标注完整处理、拆分、压缩、仅保留来源、忽略或待定，并可记录原因；
- 用户自定义内容分类；分类、准入动作、知识类型、认知角色和审核状态互不混用；
- 外部工作区词表支持大小写归一、用户确认的别名/翻译/相近词提示、显式重复词条合并，以及“分类词条 → 知识类型”处理规则；任何真实词条均不得成为源码常量或迁移 seed；
- 手工或确定性规则创建对象/概念/断言/事件/方法/框架/关系；
- AI 处理计划和结构化变更提案作为可选增强；
- 与既有知识的重复、补充、冲突和关联比较；
- 对已准入内容自动提交低风险新增和非破坏性修订，同时展示 `KnowledgeChangeSet`、AI 来源和授权依据；
- 合并、删除、重要冲突裁决和大规模结构调整转人工；
- 关键词、对象、来源、时间、关系和处理状态找回；
- 从知识返回具体文档片段、图片用途、处理运行和变更理由；
- 基本状态、错误、幂等、暂停、纠错、补偿修订和重新处理。

MVP-0A 不要求 AI、Embedding、定时采集、日报/周报、QQbot、Webhook、公共外部 API、云部署、批量外链抓取、OCR、完整图片理解、音频或视频。MVP-0B 只增加 AI 增强，不扩大这些边界。

#### 7.1.1 M1C 可运行核心检查点

为了尽快得到可使用的程序，MVP-0A 先经过一个不改变最终语义的可运行检查点。该检查点只要求：

1. 从包体外选择或上传一份固定周刊 Markdown，并把来源身份、原始 Blob、结构、Fragment 和媒体引用写入真实 PostgreSQL；
2. 用户在网页查看原文条目，分别提交内容分类和准入动作；
3. 用户从获准 Fragment 创建或修订知识项，建立一条类型化关系，并以引用多个既有修订的 Framework 知识完成一次最小重组；
4. 用户按当前已实现的文本、来源、状态和一跳关系条件搜索，并从结果返回准确 Fragment 和原文上下文；
5. 用户能够纠错、撤回或重新处理，重复导入和重复命令不产生重复副作用；
6. 整个流程在没有 AI、Embedding、外部网络或个人数据进入包体的情况下运行。

该检查点先使用一份周刊和至少三个代表性条目。十期批量运行、别名、集合、树、完整时间过滤、搜索投影、领域 Bundle 导出恢复、正式 PostgreSQL TM2、容器/浏览器发布认证和性能优化继续属于 MVP-0A 的后续增量，但不阻塞首个纵向程序运行。

截至 2026-08-16，该检查点已在固定 `ruanyf/weekly` issue 405 上通过：真实浏览器与 disposable PostgreSQL 18 完成 Git 来源导入、277 个 Fragment、三个代表性人工决定、直接来源知识项与类型化关系、引用两个既有知识修订的 Framework、一次撤回修订、文本/来源/一跳关系检索和精确 Fragment 返回；相等导入与相等知识命令重放没有产生重复副作用。该结果是本地产品功能证据，不代替正式 TM2、容器/Linux、发布或分发认证。

同日完成的 M1C-EXPAND 进一步用固定提交的第 398–407 期核验了十份原始 SHA-256，
通过正式导入器写入 10 个 Snapshot、2,639 个正式 Fragment，并返回阶段 0 冻结的
345 个审核单元。最小 `struinfo.m1c-domain.v1` Bundle 将当前 36 张领域表写入包体外
`exports/`，只携带 10 个 Blob 身份；在同一 `workspaceId` 的空数据库恢复后，逐表状态、
确定性搜索和导入命令重放保持一致。这证明十期规模与最小领域恢复可运行，但不等同于
跨工作区克隆、Blob 字节归档、非空目标合并或生产灾难恢复演练。

随后完成的 M1C-USE-1 关闭了第一次实际使用暴露的直接阻碍：导入 receipt 返回的审核
单元过去无法在重开页面后形成可操作队列。Evidence 详情现在保留 Fragment 对应的
`DocumentNode.nodeKind`，网页只把 `section` Fragment 重建为当前来源的审核队列，显示
已审核/总数、逐条前进并允许从当前条目打开精确原文。该读模型在真实 PostgreSQL 18 的
十期来源库及空库恢复副本上都得到 2,639 个 Fragment、345 个审核单元；它没有保存
用户判断、偏好或来源正文到 Git，也没有把 AI 或完整偏好评级变成使用前提。

M1C-USE-2 及后续直接使用修订根据首轮逐条审核进一步调整了实际操作边界。审核页现在把 Fragment 正文、
两个独立五档滑动评分、处理动作、快速标记、关键词与联系意图放在同一工作台：`有用程度`
写入 `information_density`，`有趣程度` 写入 `current_interest`，而 `完整处理`、`拆分`、
`压缩` 等仍是独立的 `IntakeAction`，不能由一个综合分替代。界面可根据评分和正文长度
提出处理建议，但最终动作由用户确认。用户可维护自己的快捷标记；快捷栏保存在当前外部
数据根的工作区个人偏好 JSON 中，不由源码提供默认词汇，也不进入 Git、包体或领域 Bundle。
选中标记后才会作为当前外部工作区的 `VocabularyTerm` 保存；从快捷栏删除不会重写既有审核。
关键词由无 AI 的确定性提取器给出候选，用户可以增删。自动标签具有总开关；链接目标、
URL 路径和附件文件名默认不进入候选，只保留可读的链接标题，用户可显式允许域名并维护
精确排除词。开关和筛选与快捷栏一起保存在包体外的工作区个人偏好文件中；关闭自动标签
不会删除手工添加或已经保存的词条。个人偏好接口不可用时不得阻断核心审核：网页允许在
本次页面会话新增和使用快捷标记、调整自动筛选并正常提交分类，同时明确提示这些 UI 设置
尚未持久化。恢复接口后仍以外部偏好文件为正式保存边界，不把会话回退写入源码或领域
数据库。用户还可拒绝自动联系或记录明确联系意图；
在正式 KnowledgeItem 存在以前，这些意图不是
`KnowledgeRelation`。完成一条后自动前进，返回上一条会从持久化决定、评分和词表指派
恢复界面。正式 `KnowledgeChangeSet` 编辑被移到独立的高级知识维护页，不再阻塞逐条审核。
桌面布局保留正常的工作区纵向滚动，不把整条审核流程强制压缩到一个视口，也不使用
`overflow: hidden` 遮挡下方内容。Fragment 正文可以在有界阅读区内部滚动；评分、动作、
原因、快捷栏、标签、联系和提交区则随页面内容自然展开并可顺序到达，不通过缩小可读文字
或操作目标换取空间。该增量没有新增迁移、依赖、个人资料 seed 或仓库内偏好文件。

### 7.2 MVP-1：偏好学习与每周自适应摄取

MVP-0 证明知识核心可用后，再让系统持续处理该信源并逐步学习用户偏好：

> 每周发现新一期 → 保存提交身份和快照 → 分维度评分 → 高确定性内容自动处理、低价值内容自动忽略、不确定内容人工审核 → AI 维护知识并记录探索推荐原因。

候选增量包括：

- 可恢复的每周调度、Git 游标、重试和变化检测；
- 从人工样本提议 `PreferenceProfile` 和筛选规则，并由用户批准、试运行和版本化；
- 独立的 `ExplorationPolicy`，支持邻域扩展、跨领域连接、基础缺口、新兴信号、观点多样性和偶然发现；
- 信息价值、偏好、探索、噪声和不确定性的分维度评估；
- 自动分流的阈值、数量/费用预算、暂停、解释和回滚；
- 发现冲突时建立 `ConflictCase`，并在允许站点范围内保存网络核验证据；
- 用户始终可以覆盖决定、修正规则并重新处理受影响内容；
- 基础 JSON 导出，覆盖来源、文档结构、知识、引用、规则、变更集和冲突。

核心第一版暂不包含：

- 开放网络自主发现信源；
- 未经用户启用策略的自动入库；
- AI 自动合并/删除核心词条或裁决重要冲突；
- 任意网页、登录态页面和复杂反爬站点；
- 大型知识图谱画布和预先设计的复杂本体；
- 多用户协作和多租户商业化；
- StruInfo 内部直接实现 QQ 协议；
- 云端直接访问用户局域网；
- 让网页内容触发任意工具或代码执行。

## 8. 验收场景

### 8.1 MVP-0A 无 AI 知识核心验收

1. 系统导入至少 10 期固定周刊样本，并为每期保存仓库、路径、提交身份、内容哈希、获取时间和可核验证据。
2. 文档能够稳定拆成栏目和独立条目；重复导入不产生重复 Resource、Snapshot 或知识副作用。
3. 用户可以分别标注内容分类、处理动作和可选原因，完整资料、文档结构与决定记录可以互相返回；“小说”分类不会推断处理动作。
4. 在没有 AI 配置时，用户可以从文档生成 Entry、编辑三类关键词、调整关联、按正文/关键词/来源找回 Entry，并在需要时继续创建或修订正式知识。
5. 一个包含重复、补充和冲突的样本不会被静默覆盖；每项知识和关系变更具有稳定身份、不可变修订、变更集和精确引用。
6. 用户能够按中文子串、别名、分类、对象、来源、时间和关系找回知识，查看匹配原因和图片用途，并从结果返回原始周刊上下文。
7. 用户能够纠错、撤回、产生补偿修订并重新处理；旧引用不会被语义变化后的内容冒用。
8. 用户能够导出并恢复合成工作区；搜索、树和可选向量投影删除后可以从规范数据重建。
9. 实际运行配置和个人数据位于包体外；Git、构建包和容器镜像不包含个人知识、偏好、类别、信源、快照、导出或秘密。
10. 将一份资料标记为隐私文档后，系统保存其完整原始/规范化副本；默认搜索看不到其条目或涉及这些条目的关系，明确勾选隐私查询后可以找回条目、关系并单独打开完整文档。

第 7.1.1 节的 M1C 检查点先证明第 2–7 项的最小纵向组合，并以真实 PostgreSQL 和网页可操作性为准。M1C-EXPAND 已为第 1 项的十期规模和第 8 项的最小同工作区空库恢复提供功能证据；第 8 项的完整 Blob 归档/投影重建以及第 9 项的容器制品证明仍按真实使用和发布门补齐，不得反向延迟可用版本。

### 8.2 MVP-0B AI 增强验收

1. AI 启用后为获准内容生成与手工/规则命令相同结构的处理计划和变更提案，不获得直接写表通道。
2. 自动提交的每项正式知识都有用户命令或具体策略版本作为授权依据，并能返回具体来源片段、操作来源、AI 处理运行和认知角色。
3. AI 对重复、补充、关系和冲突的建议可以逐项审核；重要冲突、合并、删除和大规模重组保持人工确认。
4. AI 未启用、超时、预算耗尽或供应商切换时，MVP-0A 的导入、维护、搜索、导出和恢复能力不降级。
5. AI 增强没有增加总体操作成本，用户愿意继续处理下一批内容，且至少一个首要指标优于无 AI 的当前做法。

### 8.3 MVP-1 验收

1. 系统按每周计划发现同一周刊仓库的新一期；休眠、重启和重复运行不会漏抓或重复提交知识。
2. AI 从人工样本生成可读的偏好规则；规则未获用户启用前不参与自动决定，启用后记录版本和适用样本。
3. 新内容分别显示信息密度、深度/广度、新颖性、当前兴趣、探索类型、噪声和不确定性，不用单一总分掩盖原因。
4. 高确定性内容按策略处理，低价值内容按策略忽略，中间区域进入审核；用户能解释、覆盖和重新训练每种结果。
5. 用户拒绝内容时可以区分“已经知道”“质量低”“暂时不需要”“不感兴趣”等原因，不会把所有拒绝都学习成领域排斥。
6. 探索策略在当前偏好之外保留可配置的内容份额，并解释邻域扩展、跨领域连接、基础缺口、新兴信号或观点多样性等展示原因。
7. 冲突网络核验只访问允许范围，保存查询和证据；无法可靠解决的冲突不会被自动裁决。
8. 抓取、解析、AI、知识提交和网络核验失败有独立且明确的状态，不会被一个“已完成”掩盖。
9. 用户能够导出来源、文档结构、知识、引用、偏好/探索规则、变更集和冲突映射。

## 9. 非功能与安全要求

- 抓取任意 URL 时防止 SSRF：禁止访问未授权的本机、内网和云元数据地址，并限制跳转、大小、类型和超时；
- 外部内容只作为数据，防止提示注入改变系统指令或工具权限；
- 抓取、解析、AI 处理、规则授权和知识提交应支持幂等；事件允许至少一次投递，但重复事件不得产生重复副作用；
- 密钥不出现在报告、消息正文或普通日志中；
- 所有自动知识写入、外部写入与推送具有身份、策略版本、范围和审计记录；
- 设置抓取并发、频率、深度、每批处理数量、网络核验和 AI 预算上限；
- 支持来源与知识删除、保留期限、导出和备份；
- 个人数据和实际运行配置不进入 Git、源码/安装目录、测试 fixture、构建包或容器镜像；
- 保存全文、图片和二级来源前记录授权与保留策略；公开部署或再分发不能以“公开可读”代替内容许可；
- 本地服务默认只监听回环地址；所有写接口仍需认证及浏览器侧 CSRF 防护，监听非本机地址必须显式开启；
- 公网在线模式必须提供认证、传输加密和私有默认可见性；
- 本地桥接只能执行能力级授权操作，不提供通用命令执行；目录授权需防止路径规范化或符号链接绕过；
- `PreferenceProfile` 与 `ExplorationPolicy` 分开授权、版本化和回滚；不得只优化点击率或既有偏好匹配率；
- 任何自动化都能暂停、解释、接管和通过补偿修订回滚，不删除既有审计历史。

- 首个真实信源是阮一峰科技周刊 GitHub 仓库；
- 以栏目中的独立条目为主要筛选单位，同时保留整期结构；
- 第一版只记录外部链接，不批量抓取全部二级来源；
- 信息价值、当前兴趣、探索价值、噪声和事实可靠性分别评估；
- `PreferenceProfile` 与 `ExplorationPolicy` 分离，探索用于抵抗信息茧房和拓宽知识面；
- 用户先人工标注，AI 随样本积累提议规则，再逐步取得自动分流和低风险入库权限；
- AI 可以自动新增和非破坏性更新；合并、删除、重要冲突裁决和大规模结构调整默认人工确认；
- 用户始终保留最高权限的暂停、接管、纠错、撤回规则和重新处理入口；
- 第一版先在网页验证入库、审核、知识浏览和搜索；报告、QQbot、外部项目接口和云部署后移；

- 无 AI 模式是正式支持的基础能力，偏好学习不阻塞知识数据库和确定性检索；
- 工程代码、外部运行配置、个人工作区数据、Blob/备份和秘密存储完全分离。
- 隐私文档完整保留，并通过显式查询范围把全文、派生条目和相关关系一起默认隐藏。

# StruInfo 产品需求草案 v0.1

- 状态：已归档，不是当前需求
- 日期：2026-08-01
- 本文目的：回答“这个项目做什么”，暂不回答“用什么技术实现”
- 当前版本：[StruInfo 产品需求](../product-requirements.md)

## 1. 当前结论

### 一句话定义

StruInfo 的长期方向是一个面向个人研究者及小型知识密集团队的、**有出处且可审核的知识结构化工作台**：它帮助用户把包括文本与图片在内的来源材料，整理成可复用的对象、概念、原子陈述及其关系，并支持检索、追溯和持续维护。

首轮验证只承诺处理文本，并将图片完整保留为来源附件。是否在首版理解图片内容、执行 OCR 或标记图片区域，要由真实样本决定。

### 用户真正雇用它完成的任务

> 当我读到或收到一批资料时，我希望系统先提出拆分、归类和关联建议，由我确认后进入正式知识库；以后我能按对象或概念找回知识、回到原始依据，并在一处安全地修改或合并重复内容。

### 它不是

- 普通文件网盘或附件管理器；
- 只靠关键词搜索的全文资料库；
- 以双向链接为主的自由笔记工具；
- 无人审核、自动宣称事实正确的“知识图谱生成器”；
- 首版就覆盖所有格式、所有领域的通用平台。

产品的核心价值不是“存下更多文件”，而是降低从资料到可维护知识的加工成本。

## 2. 要解决的问题

1. 知识被锁在长文档和图片中，只能按文件或关键词查找，难以按对象、属性或关系查询。
2. 同一概念在多处被复制；名称、描述或判断变化后，副本逐渐不一致。
3. 手工拆分、命名、消歧和建关系成本高，导致知识库很难长期维护。
4. 全自动提取容易误拆、误连或产生无依据内容，不能直接成为可信资料。
5. 摘录一旦离开原文，就可能丢失限定条件、上下文、图片区域和版本信息。
6. 普通知识图谱工具建模门槛高，而普通笔记工具又缺少约束、引用完整性和重复项治理。

## 3. 首版目标用户假设

首个用户暂定为：需要长期整理某一领域资料的个人研究者、工程师、分析师、咨询人员或内容编辑。多人实时协作暂不作为首版前提。

这个假设尚未确认。真正进入开发前，必须将它收窄为“一个具体用户 + 一个具体领域 + 一类高频资料 + 一组高频查询”。

## 4. 候选核心语义

以下模型用于检查这个想法能否自洽，不是已经冻结的数据库设计或产品契约。真实案例中的 A/B/C 可能是属性、概念、事实、步骤或论据；样本验证后才决定需要哪些类型。

### 最小用户侧对象

| 对象 | 含义 | 必须满足的要求 |
| --- | --- | --- |
| 来源 `Source` | 原始文档、文本、网页快照或图片 | 保留原件及版本，不被提取结果替代 |
| 证据锚点 `Evidence` | 原文段落、页码、字符范围或图片区域 | 能从知识一键回到准确上下文 |
| 知识对象 `Item` | 有稳定身份的实体、概念或术语，如 D | 有唯一 ID、规范名称和可选别名 |
| 原子陈述 `Assertion` | 一个可独立理解、引用和维护的陈述 | 只有一个主要语义焦点，保留必要限定条件 |
| 关系 `Relation` | 两个对象或陈述之间有方向、有类型的连接 | 可反向查询；正式关系必须经过确认 |
| 修订 `Revision` | 对象、陈述或关系的历史版本 | 小幅修订不破坏引用；语义发生实质变化时新建陈述并撤回旧陈述 |

### 来源陈述与用户知识不能混为一层

为了保证“可编辑”与“可追溯”不互相冲突，候选模型至少要区分：

1. **来源所声称的内容**：引用或忠实转述某个具体证据；确认只表示“来源确实这样说”，不表示它客观为真。
2. **用户归纳或推断**：由一个或多个来源综合得到，必须明确标注其产生方式，不能伪装成原文内容。
3. **规范对象或概念**：用于统一命名、别名和复用，本身不等于某个来源中的事实。

如果一次编辑使原证据不再支持新版文字，就不应继续沿用同一条来源陈述；应创建新的归纳/陈述，并保留旧版本及其状态。

### A/B/C 与 D 需要区分两层含义

“文档从 A、B、C 三方面描述 D”不能直接等价为“复制三段文本并挂在 D 下”。首版需要区分：

1. **可复用概念或维度**：例如“耐高温”“工作原理”“应用场景”；它们可以被 D、E 等多个对象共同引用。
2. **绑定具体对象的陈述**：例如“D 可在 800°C 环境工作”；这条陈述带有 D 的上下文和自己的来源，通常不能原样当作 E 的事实复用。

示例：

```text
来源 S1 ──证据──▶ “D 具有耐高温特性” ──about──▶ 对象 D
                         │
                         └──uses concept──▶ 概念「耐高温」

来源 S2 ──证据──▶ “E 具有耐高温特性” ──about──▶ 对象 E
                         │
                         └──uses concept──▶ 同一个概念「耐高温」
```

这里复用的是概念“耐高温”的稳定 ID，而不是把关于 D 的整条事实错误地复用给 E。

### “强关联”的产品定义

强关联不是一个模糊的高权重，而是同时满足：

- 关系类型明确且有方向；
- 目标引用稳定 ID，而非复制名称或正文；
- 已由用户确认；
- 可从两端查询；
- 有来源证据，或明确标注为用户创建/推断；
- 可撤回且保留变更历史。

### 原子陈述的拆分标准

一个原子陈述应当：

- 只有一个主要语义焦点；
- 可以被单独检索、引用和更新；
- 保留理解它所需的最小上下文；
- 不因拆分丢失否定、条件、时间、数值单位或适用范围；
- 能准确返回证据位置。

“越碎越好”不是目标。如果条件与结论分开后会失真，它们应保留在同一陈述中。

## 5. 产品原则

1. **来源与结构化结果并存**：来源是证据，不因提取完成而被丢弃。
2. **建议不等于事实**：系统可以生成候选项，但未经确认不得静默写入正式知识库。
3. **通过引用复用**：共用稳定 ID，不复制一份看似相同的文本。
4. **逐步结构化**：先允许自然语言原子陈述；关系模式稳定后再转为更严格的属性或三元组。
5. **允许冲突并存**：不同来源的矛盾陈述不互相覆盖，交由用户判断状态。
6. **可解释的自动关联**：建议必须展示目标、关系类型、理由、证据和不确定性。
7. **用户拥有数据**：结构化数据和来源映射能够导出。

## 6. 核心工作流

1. 用户创建一个知识库，并明确此次整理目的。
2. 用户粘贴文本或导入资料；系统完整保存来源。
3. 系统解析内容，提出对象、概念、原子陈述和关系候选。
4. 用户在来源与候选结果并排的审核界面中拆分、合并、改写、消歧、接受或拒绝。
5. 用户批准后，候选项才成为正式知识。
6. 用户通过关键词、对象、类型、关系或来源检索，并能双向浏览关联。
7. 新资料到来时，系统优先提示已有对象/概念、潜在重复和潜在冲突。
8. 用户可以重命名、合并、拆分或撤回；引用、来源与历史保持完整。

## 7. 需求验证关口与候选 MVP

### Gate 0：冻结 MVP 前必须完成

在选定以下内容之前，不把任何完整功能清单称为 P0：

1. 一个具体的首个用户和领域；
2. 2–3 份真实来源及人工整理的期望结果；
3. 一个首要产品结果，以及当前做法的对照基线；
4. 三个最常见的查询或维护任务；
5. A/B/C 在该领域中的实际语义和适当粒度；
6. 首版是否必须读取图片内容，还是只需保留图片证据。

Gate 0 的交付物是“真实样本集 + 期望结构 + 当前流程耗时/错误 + 首要成功指标”。通过后，才从下面的候选能力中选出完成该任务所需的最小集合。

### 候选能力池（尚非开发承诺）

| 编号 | 候选能力 | 用什么问题决定是否进入 MVP |
| --- | --- | --- |
| C-1 | 来源导入与保留 | 首轮可只支持粘贴文本；再按样本选择 Markdown 或 PDF。PNG/JPEG 先作为来源附件保留 |
| C-2 | 候选拆分 | 用户的主要成本是否确实来自拆分；候选可先用人工模拟，不要求立即实现完整自动化 |
| C-3 | 审核后入库 | 只要存在系统建议就必须具备；候选默认草稿，可接受、修改或拒绝 |
| C-4 | 来源追溯 | 如果目标知识来自资料，这是不可删除的产品约束；正式来源陈述必须有证据锚点 |
| C-5 | 复用与消歧 | 真实样本是否频繁出现同义、同名或重复概念；系统不得未经确认自动合并 |
| C-6 | 类型化关系 | 只加入前三个真实查询确实需要的关系，避免先设计通用本体 |
| C-7 | 检索与浏览 | 由真实查询决定按名称、正文、类型、对象、关系或来源中的哪些维度查找 |
| C-8 | 安全维护 | 先保证稳定引用和不丢来源；只有重复治理成为高频任务时才加入完整合并流 |
| C-9 | 数据导出 | 为保证用户拥有数据，至少定义可读的 JSON；是否首版做 UI 由使用场景决定 |

候选的关系词包括：`about`、`is_a`、`part_of`、`applies_to`、`supports`、`contradicts`、`mentions`。它们只供样本验证，不要求全部进入 MVP。`same_as` 只能人工确认；`related_to` 只作兜底，避免形成无法解释的“万物相关”。

### 常见的后续方向

- PDF 精确页码锚定、图片 OCR 与图片区域框选；
- 领域模板、自定义字段和自定义关系；
- 冲突检测、过期提醒和批量治理；
- 语义搜索与更丰富的自动关联理由；
- CSV、Markdown 或标准图数据导出；
- API 及与其他知识工具的集成。

### 当前明确不做

- 任意格式、任意领域的完美解析；
- 无人审核的自动入库、实体合并或内容覆盖；
- 复杂本体、RDF/OWL、推理引擎或专用图数据库；
- 把大型关系图画布作为核心界面；
- RAG 问答、AI 写作、自动报告等下游应用；
- 多人实时协作、复杂权限、移动端和大量第三方同步；
- 自动判断来源陈述在客观世界中是否为真；
- 高级图片理解、视频和音频处理。

## 8. 两类验收不能混淆

### 8.1 产品价值验收（主要）

选定一个真实任务，使用同一批 5–10 份资料分别完成“当前做法”和“StruInfo 原型流程”。提前写下需要回答的查询或需要完成的产出，并记录整理时间、查找时间、错误、重复项和后续维护动作。

原型只有在至少一个首要结果上显著优于当前做法，且用户愿意继续导入下一批资料时，才算产品假设成立。候选目标是整理耗时降低 30%，但最终阈值必须依据当前基线设定。

这一验证可以用纸面原型、可点击原型或人工在后台模拟系统建议完成，不需要先开发自动抽取平台。

### 8.2 D/E 模型一致性测试（次要）

准备两份真实来源：第一份从 A、B、C 三方面描述 D；第二份描述 E，并与第一份共享至少一个概念。检查：

1. 原始资料始终可以查看。
2. D、E 及各自的来源陈述能够被表达。
3. 可复用概念只保留一个规范对象，绑定 D/E 的陈述各自保留。
4. 错误拆分或错误关系可被拒绝，不会静默进入正式知识。
5. 从 D 可找到其陈述；从共享概念可反向找到 D 和 E。
6. 每条来源陈述都能返回原文位置；图片只在首版选择图片解析时要求区域锚定。
7. 对象改名后，稳定引用仍然有效。

这个场景只能证明候选语义模型自洽，不能证明产品有价值；合并、完整历史和导出只在进入最终 MVP 范围后分别验收。

## 9. 成功标准与验证

最需要验证的不是抽取模型有多聪明，而是这个闭环是否比现有做法更省力，并且在持续加入资料后仍保持可用。

### 建议验证顺序

1. **样本建模实验**：选 2–3 份真实资料，人工整理出期望结果，验证最小数据模型是否能无损表达。
2. **纸面/可点击原型**：模拟来源与候选并排审核，记录拆分、合并、拒绝和复用行为。
3. **小规模纵向试用**：连续两周加入相似和冲突资料，观察知识库是否越来越乱。
4. **再决定自动化深度**：根据重复操作和审核成本，决定哪些步骤值得自动化。

### 候选指标（需用真实基线校准）

- 100% 的正式来源型陈述可以回到证据；
- 0 条未确认的自动建议静默进入正式知识库；
- 第二次遇到同一概念时，可以复用而不产生重复对象；
- 完整整理耗时相较纯手工流程明显下降，暂以 30% 为待验证目标；
- 多数候选只需接受或小幅修改，暂以 70% 建议接受率为待验证目标；
- 给定典型查询，用户可在 30 秒内找到条目并核对原始依据。

## 10. 最大风险

| 风险 | 最小验证方式 | 失败后意味着什么 |
| --- | --- | --- |
| 用户实际只需要全文搜索或笔记 | 用真实资料比较“直接搜索”与“结构化后检索” | 缩减或重新定位产品，不继续堆图谱能力 |
| 条目粒度无法稳定 | 让同一用户隔日重拆，或让多名用户拆同一资料 | 需要领域模板和灵活结构，不能强制全局统一粒度 |
| 审核成本高于手工整理 | 记录 20 次真实导入的接受、修改、拒绝与耗时 | 优先改善审核流，不盲目提升提取复杂度 |
| 自动关联误合并 | 使用同名、别名、缩写和同名异物测试 | 只给建议；提高确认门槛和消歧信息 |
| 来源与上下文丢失 | 对测试集逐项检查限定条件和锚点 | 溯源模型不合格，不能进入更多功能开发 |
| 格式支持拖垮范围 | 统计真实样本的格式占比 | 只做覆盖率最高的 1–2 种适配器 |

## 11. 进入开发前必须确认的问题

按影响从高到低排序：

1. **第一个具体用户和领域是什么？** 他当前怎样整理，又在什么时候失败？
2. **2–3 份真实输入和期望输出是什么？** 这是确认条目粒度和模型的唯一可靠依据。
3. **A/B/C 在真实案例中分别是什么？** 是属性维度、概念、事实、论据、步骤，还是一段说明？
4. **首要结果只能选一个，是什么？** 整理更快、检索更准、消除重复、保持一致、发现联系，还是向其他系统供数？
5. **用户最常提出的三个查询是什么？** 这会决定索引、关系和界面，而不是“图谱”这个名词。
6. **结构由谁定义？** 系统预设、用户先定义，还是系统从资料中建议后由用户确认？
7. **资料的隐私、规模和运行方式是什么？** 本地或云端、个人或多人、几十篇或几十万篇、是否允许外部模型。
8. **冲突和更新如何处理？** 保留多个来源观点、标记过期、等待裁决，还是允许覆盖？

在这些问题中，前四项未确认前，不应锁定数据库、AI 模型、前端框架或部署形态。
